# Mobile Vet

Livestock protection platform for Ethiopian pastoralists: RFID-tagged herds, field health records,
NDVI/rainfall drought monitoring, risk scoring, and loan/insurance workflows, all on one shared database.

Built with Next.js 16 (App Router, Server Actions), PostgreSQL 17 in Docker and Tailwind CSS 4.

## Quick start

Requires Docker Desktop and Node 20+.

```bash
npm install
npm run db:up        # starts Postgres on localhost:5433 and loads schema + demo data
npm run dev          # http://localhost:3000
```

`.env.local` needs:

```
DATABASE_URL=postgres://mobilevet:mobilevet@localhost:5433/mobilevet
```

## Database scripts

| Command | What it does |
|---|---|
| `npm run db:up` | Start the container (first start creates and seeds the DB) |
| `npm run db:down` | Stop the container (data is kept in a Docker volume) |
| `npm run db:reset` | Regenerate the seed, wipe the volume and start fresh |
| `npm run db:psql` | Open a `psql` shell |

- Schema: `db/init/01-schema.sql`
- Demo data: `db/init/02-seed.sql`, generated by `scripts/generate-seed.mjs`. The generator is
  deterministic and every date is relative to `CURRENT_DATE`, so the data always looks current.

## How the data is related

Nothing is stored twice. Summary figures are computed live from the records:

- **Herd size, sick count, insured / has loan, last visit**: the `farmer_summary` view, built from
  animals, approved applications and completed visits.
- **Region totals** (farmers, animals, outbreaks, loans, insurance, field workers, alerts): the
  `region_summary` view. Only the climate inputs (NDVI, rainfall) are stored on `regions`.
- **Vaccination history** comes from health records of type `vaccination`.
- **Risk scores** come from `assess_farmer_risk()` in SQL, which combines regional drought (NDVI and
  rainfall), herd health (sick share, recent cases by severity, vaccination coverage), herd
  diversification, and financial position (insurance, loans, herd size). It re-runs automatically
  whenever animals, health records, applications or climate data change.
- **Alert read state** is per user (`alert_reads`).

## Access control

Roles are defined once in `lib/permissions.ts`. Every page calls `requireUser()` and every Server
Action calls `authorize()` (`lib/auth.ts`).

- Government, banks and insurers have read-only access to farmers, livestock, health records,
  visits, risk, regions and the overview.
- Every application is visible to everyone, so a farmer's existing debt with any institution shows
  up when they ask for more credit. Only the institution an application was sent to can review it,
  approve or decline it, or mark it completed (loan repaid / policy closed).
- An approved loan counts as active debt until it is marked repaid. Repaid loans build the farmer's
  repayment history, which lowers their financial risk score.
- Extension workers are limited to their assigned region.

Sessions are random tokens stored in the `sessions` table, sent as an httpOnly cookie. Passwords are
bcrypt hashes via pgcrypto.

## Project layout

```
app/(site)/        public website (home, about, services, contact → inquiries table)
app/login/         sign-in
app/dashboard/     authenticated app (overview, farmers, livestock, health, visits, risk,
                   applications, regions, alerts, users, inquiries, search)
lib/db.ts          pg pool
lib/auth.ts        sessions and authorization
lib/queries.ts     read queries (role/region scoped)
lib/actions/       Server Actions (all writes)
components/        UI kit (ui.tsx), client widgets (client.tsx), forms, charts
proxy.ts           redirects signed-out users away from /dashboard
```

The previous Supabase-based code is kept in `_legacy_supabase/` for reference. It is excluded from
the build and can be deleted.
